Questions worth asking in the demonstration

What exactly does the model decide?

It proposes among options code already allows. The existing validator checks IDs and constraints, and code ranks the options. It cannot call product tools or authorize a write.

Why does return to service need another approval?

The repair close event resumes the graph. Availability is a separate dispatcher decision, so maintenance closure alone never returns the bus.

Does a passing scenario prove production readiness?

No. The suite checks the integrated simulated system. Real API capabilities, agency rules, authentication, concurrent operators and deployment still need validation. Known gaps are explicitly reported.

Does memory make the agent more autonomous?

No. It retains structured, scoped history of successful approved incidents. Every new incident still reads current facts, passes code checks and waits for a new approval.

REPEATABLE EVIDENCE, NOT A SCREENSHOT

Evaluate the behavior. Inspect the memory.

These checks run locally against the actual system and adversarial fake model outputs. They make no paid calls.

Two distinct kinds of memory

Runtime incident memory: agency- and vehicle-scoped SQLite summaries. Only completed incidents with both approval scopes and clean invariants enter it. Reset does not clear history. Past availability, raw free text, secrets and operator details do not reach the model.

Coding-agent context: AGENTS.md and docs/AGENT_MEMORY.md point to the current implementation, decisions, verification commands and boundaries. Test results are dated evidence, not forever guarantees.

The hosted replay contains no runtime memory database. To inspect persistent memory, run the local console.
